# Step 12: REST/JSON API

Status: done
Milestone: M3 Network access
Depends on: step 11

## Goal

An HTTP/JSON API for browsers, scripts and curl, with the same semantics as gRPC.

## Decisions

[ADR 0030](../adr/0030-rest-json-api.md), refined while writing the code:

- Every operation is implemented once (`iwdb_server::ops`); gRPC and REST only add their transport.
- REST and gRPC share one port: HTTP/1.1 and HTTP/2 are detected per connection, and the content type `application/grpc...` picks gRPC.
- Messages are proto3 JSON (pbjson). `Value`, `Expr` and `Pattern` are the core's JSON form, read with the core's `from_json_str` (upstream #57, fixed), so the depth limit is 100 here too.
- Streamed answers are one merged message by default, or NDJSON chunks with `Accept: application/x-ndjson`.
- Errors carry the HTTP status of their code and an `Error` body.
- The OpenAPI 3.1 document is generated from the route table and the protos, served at `/v1/openapi.json`, checked in, tested, and linted in CI.

Changes to the plan, and why:

- **Routes** are under `/v1/namespaces/{ns}/...`, not `/v1/{ns}/...`, which would collide with `/v1/namespaces` for a namespace named `namespaces`. Batch reads are `POST .../get-nodes` and `.../get-edges`. Analytics are one route, `POST .../analyze`, with the job in the body (the proto's `Job` oneof), instead of `.../jobs/pagerank` and one route per job.
- **pbjson's `exclude`, not `extern_path`.** The three wrapper messages are our own prost types, so their serde is implemented on them directly.
- **No 64-level JSON limit.** #57 was fixed upstream (`7e7b7fa`) before this step started, so the planned restriction was never built.
- **NDJSON or one message.** Streamed answers default to one message, which is what curl and browsers want; NDJSON is opt-in. SSE stays with the change stream (step 13).

## Acceptance criteria

- [x] Conformance suite green over REST: 26 cases × 2 answer forms (`tests/conformance_rest.rs`), and unchanged over gRPC.
- [x] The OpenAPI document validates and matches the implemented routes (test). `tests/openapi.rs` checks that the checked-in copy equals the served document, every reference resolves, every schema is used, the paths and methods are exactly `ROUTES` (from which the router is built), path parameters are declared, and every RPC has a route. `tests/rest.rs` checks that every route is served and other methods get 405. CI validates the document against OpenAPI 3.1 with Redocly (`redocly.yaml`, the recommended rules; it passes with no errors or warnings).

## Non-goals

- TLS, authentication, CORS: step 15. The REST API refuses cross-site writes from browsers by requiring `application/json` bodies (ADR 0030), but has no other protection; bind the server to localhost or a private network.
- The change stream (SSE and gRPC): step 13.
- A Python REST or gRPC client: step 14. `RestRemote` is the reference for clients in other languages.
- Health and readiness endpoints and metrics: step 16.

## Result

- `iwdb-server` serves gRPC and REST on one port. `ops.rs` holds the 19 operations once, `service.rs` is the gRPC glue, and `rest.rs` holds the routes, request reading, answers and errors. `rest/json.rs` has the serde of the core's types and `rest/openapi.rs` generates the document. `serve.rs` dispatches each request by content type on hyper-util's auto (HTTP/1.1 and HTTP/2) connections.
- Tests: `conformance_rest.rs` (52 cases); `rest.rs` (10 cases: routes and 405s, error statuses and bodies, the body limit, NDJSON chunks with the meta last, 100/101 levels, single entities with percent-encoded ids, HTTP/1.1 and HTTP/2 next to gRPC, a client that goes away over HTTP/1.1, idle connections at shutdown); `openapi.rs` (5); unit tests of the JSON serde, the HTTP mapping and the REST client. All gRPC tests pass unchanged on the new accept loop. The workspace has 502 passing tests, and fmt, clippy, rustdoc and `cargo deny` pass.
- New dependencies of `iwdb-server`: axum (without default features; its router `matchit` is `MIT AND BSD-3-Clause`, so `deny.toml` now allows BSD-3-Clause), pbjson and pbjson-build, and prost-types (to read the descriptor set). http, http-body-util, bytes and tower-service were already in the tree. serde_json gains `raw_value` and `float_roundtrip`.

# ADR 0029: Rust 1.99, edition 2024, and the toolchain policy

Status: accepted
Date: 2026-10-03

## Context

Step 1 set `rust-version = "1.85"` to match `ironweaver-core`, and kept edition 2021. Ironweaver DB is a database and an application, not a library that others build on old compilers, so a low MSRV buys little. It does cost something:

- **Held-back dependencies.** `.cargo/config.toml` made the resolver fall back to versions that build on 1.85 (`tonic-prost` 0.14.6 needs 1.88, `wasip2` 1.0.4 needs 1.87).
- **An extra dependency.** `fs4` stays only because std's file locks need 1.89 (ADR 0006).
- **Two toolchains in CI.** The MSRV job tests a compiler nobody uses for releases.

How each toolchain gets into the build:

- **Wheels.** maturin-action builds them in a manylinux2014 container (glibc 2.17) on Linux and natively on macOS (arm64, and x86_64 on `macos-15-intel`). Its rustup follows `rust-toolchain.toml`.
- **Linux targets.** Rust 1.99 still supports glibc 2.17 on `x86_64-unknown-linux-gnu` and `aarch64-unknown-linux-gnu` (platform-support page of 1.99), so the manylinux image doesn't change.
- **x86_64 macOS.** `x86_64-apple-darwin` is Tier 2 with host tools since 1.90, which is enough for the Intel macOS wheel.
- **PyO3 and the core.** PyO3 0.29 needs 1.83, and `ironweaver-core` declares 1.85; ours must not be lower than the core's (ADR 0002).
- **No other pins.** There are no Docker images, and no server toolchains other than CI's.

## Decision

- **Toolchain.** `rust-toolchain.toml` stays on the floating `stable` channel, so local builds and CI get each new stable release, patch releases included (1.96.1, 1.97.1 and 1.98.1 fixed miscompilations). The `MSRV` CI job builds with exactly `rust-version`, so a bump of `rust-version` is the deliberate step, and new stable releases only have to pass CI.
- **MSRV.** `rust-version = "1.99"`. Raise it when a newer stable release has something we want, not on every release.
- **Edition.** 2024 for every crate and for `fuzz/`, with `resolver = "3"`. Resolver 3 already prefers dependency versions that support `rust-version`, so the fallback setting in `.cargo/config.toml` is gone.
- **Features.** A newer language or library feature is adopted only where it makes code safer, simpler or faster, or removes a dependency. Working code isn't rewritten for its own sake. `documentation/steps/step_11b.md` records what was adopted and what was rejected, and why.
- **Lint gate.** The Rust and MSRV jobs set `CARGO_BUILD_WARNINGS=deny` (Cargo's `build.warnings`, 1.97). A warning from rustc or clippy now fails every step, `cargo test` included; before, only the clippy step had `-D warnings`. It doesn't change the compiler flags, so unlike `RUSTFLAGS=-Dwarnings` it doesn't change the build cache. Clippy and the tests run with `--all-features` (failpoints, test helpers, the client and the conformance suite).

## Consequences

- `fs4` is gone: the data-directory lock uses `File::try_lock` and `File::try_lock_shared`. Like fs4, std uses `flock(LOCK_EX/LOCK_SH | LOCK_NB)` on Unix and `LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY` on Windows, so the semantics don't change (ADR 0006, `formats/data-dir.md`). On a Unix target where std doesn't use `flock` (Solaris since 1.98) opening fails with an `Unsupported` error; we don't ship there.
- `ironweaver-core` made the same move in `ca308f0` (edition 2024, `rust-version = "1.99"`), bumped in step 11b; our MSRV is no lower than the core's, as ADR 0002 requires.
- Contributors need Rust 1.99 or later (`rustup update`). A build on an older toolchain fails with Cargo's `rust-version` message.
- Profilers and debuggers need to demangle v0 symbols (the default since 1.97): use current `perf`, `samply`, `gdb` and `lldb`.
- On-disk formats, protos, the public API and the Python module are unchanged; the compatibility fixtures and the cross-version check in step 11b show it.

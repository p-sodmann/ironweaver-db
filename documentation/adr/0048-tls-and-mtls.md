# ADR 0048: TLS by default, certificate reload, and mTLS as an authenticator

Status: accepted
Date: 2026-10-04

## Context

Until step 15b the server spoke plain TCP: 15a's passwords, sessions and API tokens crossed the network in clear, and a non-loopback address needed `[server] plaintext_public` (ADR 0047). Step 15 asks for TLS on by default, plaintext only with an explicit flag, and client certificates (mTLS) as a way to authenticate. Points to decide: the TLS library and defaults, how a certificate is replaced, which part of a client certificate names the user, whether a client certificate is optional or required, what happens to the plaintext flags, how clients and the probe speak TLS, and how a development setup gets a certificate.

## Decision

**rustls, on the one port.** The accept loop (ADR 0027) does a rustls handshake on every connection, at most 10 s, then serves it as before. ALPN offers `h2` (gRPC and REST) and `http/1.1` (REST). The crypto provider is ring rather than rustls' default aws-lc-rs: no cmake or nasm in the Docker build. tonic's `tls-ring` uses the same rustls. TLS 1.2 and 1.3 with rustls' safe defaults. A handshake that fails (a client that doesn't trust the server, one the server doesn't trust, plaintext) ends that connection; it is logged at `debug`.

**On by default; plaintext is explicit.** `[tls] enabled = true` by default, and then `[tls] cert` and `key` (PEM files) are required: a server without them doesn't start, and the message names the alternatives. Plaintext needs `[tls] enabled = false`. On a non-loopback address it also needs `[server] plaintext_public = true`, 15a's flag, kept under its name: it now means "plaintext on a public address", which is what deployments that set it in 15a already opted into. With TLS on, `plaintext_public` has no effect and a warning says so (it doesn't stop the start, so an upgrade that turns TLS on keeps working). A certificate and key set while TLS is off are ignored with a warning, so the image's config, which names the mounted files, can still run in plaintext by two variables. `[console] public` (ADR 0041) stays refused, and its message now names `[tls]` and both flags.

**Reload on SIGHUP, not a file watch.** SIGHUP reads the certificate, key and client CA again and swaps the server configuration at once. New connections get the new one; open ones keep theirs. A reload that fails (a file missing, a key that doesn't match its certificate) keeps the configuration in use and logs an error. A file watch was rejected: it can fire between a renewal's write of the certificate and of its key and load a mismatched pair; SIGHUP needs no new dependency; and it is how nginx, HAProxy and Postgres reload. Kubernetes users pair it with a reloader sidecar, Docker users run `docker kill --signal HUP`.

**mTLS: the subject's common name is a user.** `[tls] client_ca` (PEM) turns client certificates on. A certificate a client presents is verified against it by rustls (expired or of another CA: the handshake fails). Its subject's common name (CN), present exactly once, is the name of a user of ADR 0043. A certificate never creates a user; a CN that names none, or a subject without exactly one CN, is `unauthenticated`. This is how Postgres (`clientcert=verify-full`) and CockroachDB map certificates. SAN-based mapping was left out: CN is the established convention for client identity, and a later `[tls] client_user` choice can add it without a format change. The CN is read with a small DER reader in `iwdb_server::tls` (tested on every prefix and one-byte change of a certificate never to panic) rather than an X.509 crate.

**One more authenticator, the same principal.** The gate reads the verified certificate once per connection, next to the peer address, and turns its user into a `Principal` through `Authenticate::principal_of(user)`, the same lookup behind `authenticate(token)`. The principal goes into the same `Caller`, and every operation runs through the same `Authorized<D>` (ADR 0045). There is no second authorisation path. A bearer token or session cookie in the request wins over the certificate, so a client with a certificate can still act as the user it logs in as. A REST request other than GET or HEAD that only a certificate authenticates must carry `X-Iwdb-Csrf`, as with the console's cookie (ADR 0046): a browser presents a client certificate on its own. gRPC is exempt: a page of another origin can't send a gRPC request without a preflight.

**Optional by default, required per config.** `[tls] client_auth = "optional"` (default) or `"required"`. The handshake always accepts a connection without a certificate; with `required`, the gate refuses every request that reaches its credentials (login included) with `unauthenticated` ("this server requires a client certificate"). Health and the console's pages are answered before, as ADR 0045 left them open, so probes and load balancers need no certificate. Optional is the default because required means every operator needs a certificate in their browser before the console works.

**The session cookie is `Secure` over TLS.** The REST adapter marks the console's cookie `Secure` when the request came over TLS (also when it clears it at logout). Over plaintext it stays without: browsers drop Secure cookies set over plain HTTP. Nothing is in `localStorage`.

**Clients.** `client::ClientTls { ca, cert, key }` (PEM paths) is what `Remote::connect_tls` and `RestRemote::connect_tls` trust and present: an `https://` endpoint verifies the server against `ca`, or the operating system's trust store without one (`rustls-native-certs`); TLS settings with an `http://` endpoint are `invalid_argument`. `RestRemote` connects through a small connector of its own (TCP from hyper-util, then tokio-rustls) instead of `hyper-rustls`. A connection that fails before the server answers (a TLS handshake refused on either side) is `unavailable`, with rustls' reason in the message. Python's `iwdb.connect(..., ca=, cert=, key=)` and `iwctl`'s `--tls-ca`, `--tls-cert`, `--tls-key` pass the same through. The files are read by our own PEM reader first, so no error quotes a key.

**The probe.** `iwdb-server --probe` with no address reads the same configuration as the server (file and `IWDB_*` variables): the listen port (a wildcard address as loopback) and whether TLS is on. `--probe https://host:port` or `http://host:port` asks that address. Over TLS the probe doesn't verify the server's certificate: it sends no credentials, reads only readiness, and runs next to the server, where the certificate's name needn't match `127.0.0.1`. The handshake's signatures are still checked. The Docker image's `HEALTHCHECK` is `iwdb-server --probe --config /etc/iwdb/iwdb.toml`.

**Development certificates, and none in the image.** `docker/dev-cert.sh` (openssl or LibreSSL) makes a CA and a server certificate for `localhost`, `127.0.0.1`, `::1` and `iwdb` in `docker/tls/` (git- and docker-ignored), and with `--client <user>` client certificates. `compose.yaml` mounts that directory read-only at `/etc/iwdb/tls`, where the image's config looks for `server.pem` and `server.key`. The image holds no certificate or key and refuses to start without them; CI checks both. The tests use the test-only certificates of `tests/fixtures/tls` (made by its `make.sh`, valid until 2125, an expired pair from 2001).

**Secrets.** A private key is read from its file into rustls and nowhere else: never logged, never printed by `--check-config` (it prints the path), never in an error message (errors name the file and what is wrong with it). The log test of 15a also reloads keys that fail and greps for their lines.

## Consequences

- A server upgraded from 15a without `[tls]` settings doesn't start until it has a certificate or `[tls] enabled = false` (and, on a public address, `plaintext_public`). The release notes and `config.md` say how.
- `Server::new` (in-process, tests and embedders) has no TLS until `Server::tls`, like `Server::auth`; `LaunchOptions::tls` for `launch`. The conformance suites (gRPC and REST) run over TLS with the test certificate; the role test runs in plaintext, as the operation table is the same either way.
- `Authenticate` has one more method, `principal_of`. A later authenticator (OIDC/JWT) produces a `Principal` the same way.
- The Postgres source of projections still connects without TLS; that is the client side of a projection, not the server's, and isn't part of this step.
- Certificate management (ACME, rotation) stays out: a renewal is replacing two files and sending SIGHUP.
